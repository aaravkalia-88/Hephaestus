Hephaestus, from request to evidence

Hephaestus is an installed agent skill. The agent inspects and repairs an existing frontend; a local report helper checks whether the reported scope and verification statuses agree.

This is a reference route through real files, not a record of a completed learner walkthrough. It works offline and needs no JavaScript.

Follow one repair

  1. Ask for a focused repair. skills/hephaestus/SKILL.md establishes the baseline, policy and authorized file scope.
  2. Try “Load projects”. evals/fixtures/repair-after/app.mjs handles the request and updates visible feedback. evals/serve.mjs supplies labeled, synthetic responses.
  3. Observe the result. evals/browser-check.mjs → runChecks() exercises request states and checks the actual DOM at three widths.
  4. Read the evidence. skills/hephaestus/scripts/check-report.mjs → validateReport() checks report consistency. It does not execute or authenticate the recorded checks.

Three code stops

1. Which changes are allowed?

Start in SKILL.md, “Establish the baseline” and “Plan and repair”. The policy comes from policy/frontend-policy.json; approved brand and business exceptions must survive.

2. What changes when a request fails?

Open the repaired request handler and follow its fetch, validation and feedback paths. Compare the retained input. The server returns a real simulated error; the frontend must not turn it into invented success.

3. What does a passing checker prove?

Open validateReport and its tests. A valid report can still be incomplete. fixed_unverified and a skipped browser check cannot become verified merely because JSON parsed.

To change this, start here

  • Frontend policy: skills/hephaestus/policy/frontend-policy.json.
  • Fixture layout and focus: evals/fixtures/repair-after/styles.css.
  • Request scenarios: evals/serve.mjs and tests/fixture.test.mjs.
  • What counts as proof: evals/browser-check.mjs and the actual results under evals/results/runnable-repair/.

A practice to reuse

Write down one observable result before changing code. Here, “a delayed request shows feedback” became a browser assertion that failed on the original fixture. Running the same check after the repair is stronger evidence than saying the code looks right. Keep source facts, rendered behavior and subjective design judgments separate.

Run it again

With Node 22+, run npm run demo from the repository. Open http://127.0.0.1:4173/before/ and /after/, select a test response and press “Load projects”. Stop the server with Ctrl+C. Run npm test for the report and server contracts.
